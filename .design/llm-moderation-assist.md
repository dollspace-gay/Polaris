# Feature: LLM moderation assist (gRPC Recommend RPC + autonomous-with-override)

## Summary

Hand-moderating a Bluesky-scale firehose doesn't scale. Polaris already
has a mature gRPC classifier substrate — `Classify`, `ClassifyStream`,
`Feedback`, and `HealthCheck` RPCs at
[`proto/polaris-classifier-v1.proto`](proto/polaris-classifier-v1.proto)
with circuit-breaker, concurrency budget, and privacy-enforced
feedback — that operators use to route ML-model outputs into the
pattern engine as `Observation` signals. That substrate is the right
plumbing for an LLM moderation advisor; it lets Polaris stay LLM-
agnostic (operators bring their own model behind a thin gRPC adapter)
while reusing every safety + observability primitive already in place.

This design adds a fifth RPC, `Recommend(RecommendRequest) →
RecommendResponse`, that takes a hydrated case bundle and returns a
structured moderation judgment. The recommendation is consumed in
three operator-selectable modes, configured per policy in the workbook
designed in `.design/mod-policy-workbook.md`:

- **`manual`** (default) — the recommendation surfaces in the case
  view as an advisory panel alongside existing observations.
  Moderator decides; nothing fires automatically.
- **`assisted`** — the recommendation is materialised as a *draft
  action* in a per-moderator review queue. Moderator clicks approve
  (action emits) or reject (audit + feedback). Nothing reaches
  atproto without a human click.
- **`autonomous`** — when the LLM's confidence exceeds the policy's
  `autonomous_confidence_threshold` AND the recommended action kind is
  in `autonomous_action_kinds` AND none of the safety floors (REQ-S1
  through REQ-S7) trip, the action is created AND emitted to atproto.
  The human reverses if wrong; reversals feed back via the existing
  `Feedback` RPC.

The autonomous mode is the load-bearing capability — that's what
makes moderation scale — but every other mechanism in this design
exists to make autonomous safe enough to ship. Six layers of
defence: confidence floors, action-kind gating, subject-level
cooldowns, rate limits, a reversal-rate circuit breaker, and a
kill-switch — each independently sufficient to stop a runaway
agent.

This design depends on `.design/mod-policy-workbook.md` (the
workbook + autonomy-control fields it defines).

## Requirements

### A. Wire contract — gRPC extension

- REQ-A1: Extend
  [`proto/polaris-classifier-v1.proto`](proto/polaris-classifier-v1.proto)
  with a new RPC:
  ```protobuf
  rpc Recommend(RecommendRequest) returns (RecommendResponse);
  ```
  Same service, same circuit-breaker, same concurrency budget, same
  health probe. Operators wire any LLM (Anthropic, OpenAI, local
  Llama, etc.) behind a small adapter that implements this RPC.

- REQ-A2: `RecommendRequest` message carries the hydrated case
  bundle:
  - `string event_id` — UUID v7 generated by Polaris; the LLM echoes
    it back for trace correlation.
  - `string subject_did` — the subject's DID.
  - `string subject_kind` — `'account' | 'post'`.
  - `string incident_id` — the incident the subject sits inside.
  - `repeated Report reports` — the reports that triggered the
    case (category, body, reporter DID).
  - `repeated Observation observations` — all `Observation` rows
    on this subject including classifier signals, pattern detector
    output, upstream labels.
  - `repeated PriorAction prior_actions` — chronological prior
    actions on this subject with their cited policies + reasoning.
    This is the *precedent corpus* the LLM grounds against.
  - `repeated PolicyClause policies` — every current-version
    `mod_policies` row whose `scope` covers this subject's kind.
    Includes `decision_criteria`, `examples_positive`,
    `examples_negative`, and the `linked_label_value`.
  - `string subject_context` — when subject is a post: the post
    text, embeds (image alt-text), reply parents one level deep.
    When subject is an account: handle, display name, bio, post
    history sample.
  - `int32 max_response_tokens` — operator-configurable hint; the
    adapter may truncate to this.

- REQ-A3: `RecommendResponse` carries the structured judgment:
  - `string event_id` — echoed.
  - `string model` — what produced this (e.g.
    `"claude-sonnet-4-6"`); audited.
  - `string model_version` — same role.
  - `string prompt_template_id` — opaque-to-Polaris identifier the
    adapter uses to identify which prompt it ran; the adapter is
    responsible for stable versioning. Audited.
  - `repeated RecommendedAction recommended_actions` — usually
    one; multiple allowed for cases where the LLM thinks several
    independent actions apply. Each `RecommendedAction`:
    - `string action_kind` — one of `label | warn | takedown |
      escalate | no_action`. Must be in the `actions.kind` enum.
    - `string label_value` — when `action_kind == 'label'`; must
      match the operator's declared `label_values` set.
    - `string subject_scope` — `'account' | 'post'`; required to
      be `'post'` if `action_kind == 'takedown'` for autonomous
      eligibility (REQ-S2).
    - `float confidence` — 0.0 ≤ x ≤ 1.0.
    - `repeated string cited_policy_identifiers` — at least one;
      every identifier must be present in the input `policies`.
    - `string reasoning` — Markdown text. ≥10 chars (matches the
      `actions.reasoning` constraint).
    - `repeated string caveats` — non-blocking notes the LLM wants
      the moderator to see (e.g. "I'm uncertain whether this is
      satire; consider checking the account's pinned post").
  - `string overall_reasoning` — optional; a synthesis paragraph
    when multiple recommended actions need framing.
  - `int32 input_tokens` — for observability.
  - `int32 output_tokens` — for observability.

- REQ-A4: `Recommend` calls reuse the existing per-classifier
  semaphore + circuit breaker from
  [`polaris-backend/src/classifier/budget.rs`](polaris-backend/src/classifier/budget.rs)
  and
  [`polaris-backend/src/classifier/circuit.rs`](polaris-backend/src/classifier/circuit.rs).
  No new resource-control primitives.

- REQ-A5: Default timeout is **15 s** (higher than `Classify`'s 500 ms
  default — LLM inference is slow). Operator-configurable per-
  classifier via the existing classifier config. Timeouts increment
  the breaker counter just like `Classify` does.

### B. Recommendation observation

- REQ-B1: Every `Recommend` call's response is persisted as a new
  `Observation` row alongside existing kinds. Add a variant
  `LlmRecommendation` to
  [`polaris-types/src/observation.rs`](polaris-types/src/observation.rs)'s
  `ObservationKind` enum (today: `image_hash_cluster`,
  `account_cohort`, `reply_brigade`, `report_volume_anomaly`,
  `external_label`, `classifier_signal`).

- REQ-B2: The `LlmRecommendation` observation's `evidence` JSONB
  carries the full `RecommendResponse` payload verbatim (for audit
  + replay) plus a content-hash of the `RecommendRequest` for
  determinism checks (REQ-D2).

- REQ-B3: Observations of kind `LlmRecommendation` are surfaced in
  the existing case-view observation panel under their own visual
  treatment (distinct chip + colour) so the moderator instantly
  sees "this came from an LLM, not from a deterministic detector".

### C. The dispatcher

- REQ-C1: A new module
  `polaris-backend/src/llm/recommend_dispatcher.rs` is the single
  entry point that decides whether to call `Recommend`, what to
  send, what to do with the response, and whether to auto-fire.
  Mirrors the existing
  [`polaris-backend/src/classifier/fanout.rs`](polaris-backend/src/classifier/fanout.rs)
  shape but routes one case at a time rather than fanning a
  firehose event to many classifiers.

- REQ-C2: Triggered by:
  - **Pull** — a moderator opens a case in the dashboard; the
    case view fires `POST /api/cases/:id/llm-recommendation` to
    request a fresh recommendation. Useful when the operator
    wants the LLM's read of a case the moderator is actively
    working.
  - **Push** — a new report arrives on a subject that has at least
    one policy in `autonomy_mode ∈ ('assisted', 'autonomous')`
    covering its kind. The ingest path enqueues the case for the
    dispatcher; the dispatcher processes the queue at a
    configurable rate.
  - **Manual replay** — an admin endpoint POSTs a case-id list to
    `POST /api/admin/llm/replay` to dry-run recommendations against
    historical cases. Used for the calibration workflow (REQ-F1).

- REQ-C3: For each case the dispatcher processes:
  1. Hydrate the `RecommendRequest` from DB
     (`polaris-backend/src/llm/case_context.rs`, new). Joins:
     `subjects`, `incidents`, `reports`, `observations`,
     `actions` (limited to the subject's history), `mod_policies`
     (current versions of policies whose `scope` covers this
     subject).
  2. Call `Recommend` via the existing classifier client trait
     (extended with `async fn recommend(...)`).
  3. Persist the response as an `LlmRecommendation` observation
     (REQ-B1).
  4. For each `RecommendedAction` in the response:
     - Look up the *most permissive* cited policy's
       `autonomy_mode` (one cited policy in `autonomous` mode is
       enough to consider auto-fire; details in REQ-D3).
     - Run the safety floors (REQ-S1 through REQ-S7). If any
       trips, downgrade to `assisted`.
     - Apply the per-mode behaviour:
       - `manual` → done; the recommendation sits in the case view.
       - `assisted` → write a draft action into the
         `pending_auto_actions` queue (REQ-E1) for moderator
         approval; no atproto emit yet.
       - `autonomous` → create the action with `actor_kind =
         'autonomous_agent'`, cite the LLM-cited policies at their
         current versions, attach a reference to the
         `LlmRecommendation` observation in the action's audit
         tail, emit to atproto via the existing labeler emitter
         path.

- REQ-C4: All steps in REQ-C3 are wrapped in a single span the
  existing OTel exporter picks up. The span includes attributes
  for `case_id`, `policy_identifier`, `recommended_kind`,
  `confidence`, `final_mode_applied`, `safety_floors_tripped` so
  the operator can grep traces for "why didn't this auto-fire?".

### D. Safety floors (the things that stop a runaway)

These are server-side invariants enforced in the dispatcher AND in
the action-create API; bypassing the dispatcher (e.g. via direct DB
manipulation) won't get past the action-create layer either.

- REQ-S1: **Confidence floor.** Auto-fire requires
  `recommended_action.confidence ≥
  policy.autonomous_confidence_threshold`. Below floor downgrades
  to assisted; if also below `assisted_confidence_threshold`,
  downgrades to manual (case view only).

- REQ-S2: **Action-kind gate.** The recommended kind must be in
  the cited policy's `autonomous_action_kinds`. Additionally, the
  global eligible set (workbook REQ-G1) restricts to
  `{label, warn, takedown}` — `escalate`, `mute`, `no_action`,
  `reverse` can never auto-fire regardless of policy config.

- REQ-S3: **Account-takedown gate** (REQ-G2 from workbook).
  `takedown` may only auto-fire if the subject's kind is `post`.
  Account-level takedowns are always human-required.

- REQ-S4: **Subject cooldown.** If the subject has been ruled on
  by a human in the last N days with `kind ∈ {no_action,
  reverse}`, the dispatcher refuses to auto-fire. The human said
  "this is fine" or "the prior action was wrong"; the agent does
  not override that decision without human re-review. N default
  30 days, operator-configurable via
  `POLARIS_AUTONOMOUS_SUBJECT_COOLDOWN_DAYS`.

- REQ-S5: **Per-policy rate limit.** No more than M autonomous
  actions per policy per hour. M default 60 (one per minute
  sustained); configurable per policy via a new
  `autonomous_rate_limit_per_hour INTEGER` column on
  `mod_policies` (this is a workbook-design addendum — file a
  follow-up issue against the workbook design once both are
  approved). Exceeding the limit downgrades to assisted and
  records a `rate_limit_tripped` metric increment.

- REQ-S6: **Reversal-rate circuit breaker.** A sliding 7-day
  window of autonomous actions per policy: if the human-reversal
  rate exceeds R%, the dispatcher writes
  `autonomous_paused_until = now() + 24 hours` to the policy row
  and emits a structured alert. R default 15% (one in seven
  autonomous actions reversed by humans is the signal "the LLM is
  miscalibrated for this policy; stop"). Configurable per policy.

- REQ-S7: **Kill switch.** `POST /api/admin/llm/pause` and
  `DELETE /api/admin/llm/pause` are admin-only one-click toggles
  that set/clear a global pause flag. While paused, *every*
  `Recommend` call gets its effective mode downgraded to
  `manual`. Used in incident response; the operator never has to
  remember per-policy state to stop the bleeding.

- REQ-S8: **CSAM hard block** (REQ-G3 from workbook). A policy
  marked `human_required_always = TRUE` cannot ever auto-fire
  regardless of any other config. Enforced at the dispatcher AND
  the action-create API.

### E. Assisted-mode queue

- REQ-E1: New table `pending_auto_actions` materialises assisted-
  mode drafts:
  - `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`.
  - `incident_id UUID NOT NULL REFERENCES incidents(id)`.
  - `subject_id UUID NOT NULL REFERENCES subjects(id)`.
  - `recommended_action JSONB NOT NULL` — full `RecommendedAction`
    payload from the LLM.
  - `llm_observation_id UUID NOT NULL REFERENCES observations(id)`
    — pointer to the `LlmRecommendation` observation backing this
    draft.
  - `cited_policy_versions JSONB NOT NULL` — snapshot of
    `[{identifier, version}]` so the moderator's eventual
    approve-click cites the policy versions the LLM saw.
  - `state TEXT NOT NULL DEFAULT 'pending'` — `pending | approved
    | rejected | superseded | expired`.
  - `claimed_by_moderator_id UUID REFERENCES moderators(id)` —
    set when a moderator opens the case (mirrors the existing
    case-lock pattern in `incidents.locked_by`).
  - `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
  - `resolved_at TIMESTAMPTZ`.
  - `expires_at TIMESTAMPTZ NOT NULL` — default `now() + 7 days`.
    After expiry the row state transitions to `expired` and the
    LLM is asked to re-recommend if the case is still open.

- REQ-E2: Endpoint `GET /api/queue/pending-auto-actions` returns
  the moderator's claimable + claimed drafts. Filtered by the
  moderator's allowed policies via the existing
  `subject_routing` table.

- REQ-E3: Endpoint `POST /api/queue/pending-auto-actions/:id/approve`
  promotes the draft into a real action (calls the existing
  action-create handler with the recommended payload, sets the
  draft row to `approved`). The action's `actor_kind` is
  `'human'` — the moderator owns the decision, not the LLM, when
  the LLM was assistive.

- REQ-E4: Endpoint `POST /api/queue/pending-auto-actions/:id/reject`
  records the rejection with an optional moderator reasoning
  string, sets the draft to `rejected`, and fires a `Feedback`
  RPC to the classifier (REQ-G1) so the LLM gets the negative
  signal.

### F. Audit-trail discipline

- REQ-F1: Every autonomous action records additional audit fields
  beyond what human actions record. Add to the existing `actions`
  table:
  - `actor_kind TEXT NOT NULL DEFAULT 'human'` — `'human' |
    'autonomous_agent'`.
  - `llm_observation_id UUID REFERENCES observations(id)` —
    when `actor_kind = 'autonomous_agent'`, points at the
    `LlmRecommendation` observation that produced this action.
    The observation's `evidence` JSONB has the full LLM response
    payload (REQ-B2) for replay.
  - `model TEXT` — e.g. `"claude-sonnet-4-6"`. Snapshotted from
    `RecommendResponse.model` (REQ-A3).
  - `model_version TEXT` — same.
  - `prompt_template_id TEXT` — same.
  - `recommendation_confidence REAL` — same.
  - `input_hash TEXT` — SHA-256 of the canonicalised
    `RecommendRequest` payload. Lets a future audit verify that
    the same case wouldn't produce a different decision (replay
    determinism check) — see REQ-D2.

- REQ-F2: A reversal action against an autonomous action is
  treated specially in the audit log: the audit event includes
  the original action's full audit envelope (model, prompt
  template, LLM response, input hash) so an investigator can read
  the reversal AND the bad decision it overturned in one query.

- REQ-F3: The existing audit-log hash chain (per design.md §6)
  binds the LLM action audit envelope as one cohesive payload —
  post-hoc tampering with "what the LLM said" is detectable.

- REQ-F4: A new admin page `/admin/llm/audit` lists recent
  autonomous actions with their cited policies, confidence, and
  reversal state. Filters: `?model=`, `?policy=`, `?reversed=`,
  `?from=`, `?to=`. This is the operator's primary "what is my
  agent doing?" surface.

### G. Feedback loop

- REQ-G1: When a moderator reverses an autonomous action, the
  existing classifier `Feedback` RPC is called with the original
  case envelope and the moderator's reasoning. The
  `FeedbackRequest` is extended with two optional fields:
  - `bool was_recommendation_taken` — `false` for reversal.
  - `string reversal_reasoning` — the moderator's stated reason.

- REQ-G2: When a moderator rejects an assisted-mode draft (REQ-
  E4), the same `Feedback` RPC fires with `was_recommendation_taken
  = false`.

- REQ-G3: When an autonomous action's `reversible_until` window
  elapses with no reversal, a daily batch job fires `Feedback`
  with `was_recommendation_taken = true` (positive signal:
  the action stood). This closes the loop for the LLM to learn
  from its successful decisions, not just its mistakes.

- REQ-G4: The classifier feedback envelope keeps its existing
  privacy floor — no moderator identity in the payload, only the
  case data + outcome.

### H. Calibration / dry-run

- REQ-H1: `POST /api/admin/llm/dry-run` accepts
  `{ policy_identifier: string, lookback_days: int }` and
  enqueues a job that replays every closed case from the
  lookback window through the LLM in *no-side-effect* mode (no
  observation persistence, no action create, no atproto emit).
  The job records `{ case_id, what_lll_would_recommend,
  what_human_did, match: bool }` per case.

- REQ-H2: Endpoint `GET /api/admin/llm/dry-run/:job_id` returns
  the calibration report: agreement rate, false-positive rate,
  false-negative rate, a sample of disagreements with full case
  context. The operator reads this before flipping a policy to
  `autonomous`; the workbook UI for policy autonomy edit shows a
  "run calibration" button that kicks this job and prevents
  saving `autonomy_mode = autonomous` until at least one
  calibration run has happened in the last 30 days.

### I. Observability

- REQ-I1: New metrics in
  [`polaris-backend/src/api/metrics.rs`](polaris-backend/src/api/metrics.rs):
  - `polaris_llm_recommend_total{model, policy, kind}` —
    counter.
  - `polaris_llm_recommend_duration_seconds{model}` — histogram.
  - `polaris_llm_recommend_confidence{policy, kind}` —
    histogram.
  - `polaris_llm_autonomous_action_total{policy, kind}` —
    counter.
  - `polaris_llm_autonomous_reversal_total{policy, kind}` —
    counter.
  - `polaris_llm_safety_floor_tripped_total{policy, floor}` —
    counter (floors: `confidence`, `cooldown`, `rate_limit`,
    `csam_block`, `account_takedown_block`, `circuit_breaker`,
    `global_pause`).
  - `polaris_llm_assisted_queue_depth{policy}` — gauge.

- REQ-I2: Structured log events at INFO for every autonomous
  action emit (including the floor checks that passed) and at
  WARN for every safety-floor trip + every reversal. The fields
  are picked up by the existing tracing-subscriber JSON exporter.

### J. Frontend surface

- REQ-J1: Case-view sidebar gets a new component
  `polaris-frontend/src/components/llm_recommendation_panel.rs`.
  Renders the latest `LlmRecommendation` observation with:
  - Model + version chips.
  - Confidence bar.
  - Recommended action(s) with policy citations linked to the
    workbook detail pages.
  - LLM reasoning (Markdown rendered).
  - Caveats list.
  - For `manual` policies: "Use as draft" button that pre-fills
    the action composer.
  - For `assisted` policies with a `pending_auto_actions` row:
    "Approve draft" / "Reject draft" buttons.
  - For `autonomous` policies where the action already fired:
    a banner reading "Autonomous agent took action X at T;
    reversible until T+30d" with a "Reverse" affordance.

- REQ-J2: New page
  `polaris-frontend/src/pages/admin_llm_audit.rs` renders the
  audit list (REQ-F4).

- REQ-J3: New page
  `polaris-frontend/src/pages/admin_llm_dry_run.rs` renders the
  calibration report (REQ-H2) with a chart of
  agreement-by-confidence-band.

### K. Operator-doc surface

- REQ-K1: New doc `docs/ops/llm-moderation.md` covers:
  - Wire-up tutorial (run a fixture LLM adapter on
    `127.0.0.1:50052`, point Polaris at it, watch a recommendation
    appear).
  - Per-policy autonomy enablement walk-through with dry-run
    calibration step.
  - Safety floors in plain language ("we will not auto-takedown an
    account, we will not auto-act on CSAM, we will not auto-act
    if a human said no_action in the last 30 days, …").
  - Kill-switch usage.
  - Reading the audit page.

## Acceptance Criteria

- AC-1: `proto/polaris-classifier-v1.proto` adds the `Recommend`
  RPC and its message types. `polaris-classifier-proto` re-builds.
  Generated client + server stubs compile.

- AC-2: `polaris-backend/src/classifier/client.rs` extends the
  `ClassifierClient` trait with `async fn recommend(...)` and
  `TonicClassifierClient` implements it. `FixtureClassifierClient`
  implements it with a configurable canned response for tests.

- AC-3: The `Observation` enum + DB migration get an
  `LlmRecommendation` variant; case-view queries surface it.

- AC-4: `pending_auto_actions` table migration applies cleanly;
  CRUD repo in `polaris-backend/src/repo/pending_auto_actions.rs`
  uses `sqlx::query!` exclusively (parameterized only).

- AC-5: `actions` table gets `actor_kind`,
  `llm_observation_id`, `model`, `model_version`,
  `prompt_template_id`, `recommendation_confidence`, `input_hash`
  columns. Action-create paths from existing endpoints set
  `actor_kind = 'human'` and leave LLM columns NULL.

- AC-6: REQ-S1 through REQ-S8 safety floors are each covered by a
  regression test in `polaris-backend/tests/llm_safety_floors.rs`.

- AC-7: REQ-C3 dispatcher round-trip is covered by an integration
  test in `polaris-backend/tests/llm_dispatcher_e2e.rs` using
  `FixtureClassifierClient`. The fixture returns a canned
  `RecommendResponse`; the test verifies the resulting
  observation + (depending on mode) draft or action.

- AC-8: REQ-F1 audit columns are populated on every autonomous
  action. Existing
  [`polaris-backend/tests/tracing_action_id.rs`](polaris-backend/tests/tracing_action_id.rs)
  is extended with the autonomous-action case.

- AC-9: REQ-H1 dry-run job replays a fixture corpus of 20 closed
  cases through `FixtureClassifierClient` and emits an agreement
  report. Covered by
  `polaris-backend/tests/llm_dry_run.rs`.

- AC-10: REQ-J1 panel renders against a populated
  `LlmRecommendation` observation. CSS at
  `polaris-frontend/styles/llm-recommendation-panel.css` passes
  the `styles_coverage`, `styles_tokens`, `styles_contrast` tests.

- AC-11: `docs/ops/llm-moderation.md` exists and points an
  operator at the fixture-adapter walkthrough; the fixture
  adapter ships under `examples/` and is exercised by
  `tests/llm_fixture_adapter.rs`.

- AC-12: `cargo build`, `cargo clippy --workspace --all-targets
  -- -D warnings`, `cargo test --workspace`, `cargo fmt --all
  --check` all pass on the changed tree.

### Privacy boundary

- The `RecommendRequest` carries case content (post text, observation
  evidence, prior action reasoning, policy clauses, reports) but
  **never** carries moderator identities. The `actions.moderator_id`
  field is omitted from `PriorAction`; only the *outcome* + cited
  policies + reasoning travel.
- The `Feedback` envelope similarly excludes moderator identity.
  When a reversal happens, the LLM learns "this action was reversed
  with reasoning Y" but not "moderator alice@example.org reversed
  it". This is the same floor the classifier `Feedback` path enforces
  today.
- The operator's deployment may use a cloud LLM (Anthropic, OpenAI)
  — that traffic crosses an organisational boundary. The same opt-in
  consent banner the classifier integration shows
  (per `docs/ops/classifier-integration.md`) is reused; admin must
  explicitly enable a non-local LLM adapter with a single-field
  flag `POLARIS_LLM_EXTERNAL_OK = true`.

## Out of scope

- Polaris hosting its own LLM. The operator brings the model behind
  the gRPC adapter. (Same posture as the classifier integration.)
- Training / fine-tuning. The `Feedback` loop emits signal back to
  the adapter; what the adapter does with it (RAG corpus, fine-
  tuning, RLHF, nothing) is the adapter's choice.
- Multi-turn dialogue with the LLM (clarifying questions back and
  forth). Single-shot per case; if the LLM wants the moderator's
  attention it surfaces `caveats`.
- Cross-incident batching of recommendations. Each case is its own
  `Recommend` call. Sophisticated batching is a future optimisation.
- LLM-driven *report triage* (which reports are real vs.
  brigading-noise). That's a related but separate problem and the
  classifier substrate already partly addresses it via
  `report_volume_anomaly` observations.

## Open questions

<!-- OPEN: A4-timeout -->
### Q1: `Recommend` default timeout

15 s vs. 30 s vs. 60 s. The slower the timeout, the more LLM calls
that succeed (good); the slower a case sits with no answer (bad
for moderator UX); the longer the circuit-breaker takes to detect
a wedged adapter.

Lean: 15 s as default, operator-configurable per-classifier in the
existing classifier config block. Most LLM responses on this kind
of structured task land in 5–10 s; 15 s gives headroom without
making the case view feel sluggish.

**To resolve**: Edit this section with your decision.
<!-- /OPEN -->

<!-- OPEN: S4-cooldown-window -->
### Q2: Subject cooldown window (REQ-S4)

How long after a human moderator rules `no_action` or `reverse` on
a subject should the autonomous agent be locked out of acting on
that subject? Options:

- **(a)** 30 days (proposed default). Long enough that a human's
  "this is fine" carries real weight; short enough that the agent
  re-engages when behaviour might have changed.
- **(b)** 7 days. Faster re-engagement; relies more on the agent
  catching up.
- **(c)** Forever, until another human action. Strictest. Agent
  only ever acts on subjects no human has already considered or
  on subjects where the human action was `label`/`takedown`/`warn`
  (an affirmative action that doesn't bind the agent).

Lean: (a). Configurable via
`POLARIS_AUTONOMOUS_SUBJECT_COOLDOWN_DAYS`.

**To resolve**: Edit this section with your decision.
<!-- /OPEN -->

<!-- OPEN: S6-reversal-rate -->
### Q3: Reversal-rate circuit breaker threshold (REQ-S6)

What reversal rate within a 7-day window auto-pauses a policy?

- **(a)** 15% (proposed default). One reversal in seven; the
  agent is wrong often enough that we should stop trusting it for
  this policy until a human re-tunes.
- **(b)** 10%. Tighter; more sensitive to bad calibration.
- **(c)** 25%. Looser; tolerates more noise.

These should be operator-configurable per policy regardless.

Lean: (a).

**To resolve**: Edit this section with your decision.
<!-- /OPEN -->

<!-- OPEN: C2-push-rate -->
### Q4: Push-trigger rate-limiting

REQ-C2 push-trigger fires on new reports against subjects with
covering autonomous policies. Without rate-limiting, a brigading
event could trigger thousands of `Recommend` calls. Options:

- **(a)** Per-subject debounce: if a `Recommend` ran on this
  subject in the last N minutes, skip. N default 15 min.
- **(b)** Per-incident debounce: same idea but at the incident
  level (related-subjects share a debounce timer).
- **(c)** Hard queue depth ceiling: if `pending_auto_actions`
  exceeds K rows, push-triggers stop until depth recovers.

Lean: (a) + (c) together. Per-subject debounce stops obvious
duplication; queue-depth ceiling stops catastrophic ingest
backups.

**To resolve**: Edit this section with your decision.
<!-- /OPEN -->

<!-- OPEN: J1-confidence-display -->
### Q5: Confidence visualisation in the case-view panel

REQ-J1 shows confidence as "a bar". Three options:

- **(a)** Single horizontal bar with a colour gradient (red at
  0%, yellow at threshold, green at 100%).
- **(b)** Two bars: one for the confidence value, one ghost-bar
  showing the policy's `autonomous_confidence_threshold` so the
  moderator can see "this almost auto-fired" at a glance.
- **(c)** Numerical only — `0.83 (autonomous threshold: 0.95)`.

Lean: (b). The threshold context is the operator's most
common question.

**To resolve**: Edit this section with your decision.

## Dependencies

This design depends on `.design/mod-policy-workbook.md`:

- The workbook's `mod_policies` table is the source of policy
  clauses the LLM reads (REQ-A2 `PolicyClause` items).
- The workbook's `autonomy_mode`, `autonomous_action_kinds`,
  `autonomous_confidence_threshold`,
  `assisted_confidence_threshold`, `autonomous_paused_until`
  fields are what the dispatcher consults to decide what to do
  with each `RecommendedAction`.
- The workbook's safety floors (REQ-G1, REQ-G2, REQ-G3) are
  enforced by this design's safety-floor module
  (REQ-S2, REQ-S3, REQ-S8) — they're stated in both designs
  because they must hold at *both* layers (workbook prevents
  unsafe config; dispatcher prevents unsafe action even if the
  config slipped through).

The workbook must ship first. This design's PR cannot land until
the workbook PR is merged.

## Followups (out of this design's scope)

After this design ships, additional work that becomes possible
but does not block the initial ship:

- Multi-model ensembling: route the same case to two LLMs and only
  auto-fire on agreement. (Adapter-side trick; no Polaris changes
  needed.)
- LLM-suggested *policy amendments*: an LLM that sees recurring
  edge-cases could suggest new clauses for the workbook. Surfaces
  as a draft amendment in `mod_policies` history; admin
  approves/rejects. Worth its own design doc once the base ships.
- Operator-curated few-shot examples: bigger `examples_positive` /
  `examples_negative` arrays surfaced to the LLM as the precedent
  corpus, with a UI to add a case to the corpus after it's
  resolved.
- LLM-driven appeals review: when a subject appeals an autonomous
  label, route the appeal to a different LLM (or the same one with
  an appeal-mode prompt) for a recommendation to a human reviewer.
- Cross-instance recommendation sharing: two Polaris deployments
  could share `LlmRecommendation` observations as upstream
  signals to each other (with privacy floors). Separate design.
