# M5 design — Issue #42: Define Polaris-owned NSIDs for cross-instance federation

## Summary

Author Lexicon JSON for Polaris-owned record types (incidents, observations,
escalations, evidence pointers) and use `proto-blue-codegen` to produce typed
Rust bindings in a new `polaris-lexicons` crate. This is the wire-protocol
foundation that #43 federation, future ATProto-native interop, and any
third-party tooling building against Polaris will all depend on. v1 ships
without Polaris NSIDs by design; this issue introduces a *parallel* wire
surface that does not disturb the existing internal `polaris-types`.

## v1 connection points

- `.design/polaris-proto-blue-integration.md` §E ("Internal data model stays
  plain Rust") explicitly defers Polaris-owned NSIDs to v2. The v1 internal
  model lives in `polaris-types` as plain `serde`-derived Rust structs with no
  Lexicon dependency.
- `.design/polaris-proto-blue-integration.md` Out of Scope: "Defining
  Polaris-owned NSIDs (`polaris.incident`, `polaris.observation`, etc.).
  Deferred to a future iteration; folded into `design.md` §10's federation
  question."
- `design.md` §10 lists "Federation of moderation conversations" as an open
  question — federation cannot work without a stable wire format, which is
  what this issue provides.
- Builds on the existing proto-blue dependency: `proto-blue-codegen` is the
  Lexicon-to-Rust generator and `proto-blue-lexicon` is the runtime
  validation engine. Neither is currently a Polaris dependency (v1 only
  consumes already-generated lexicons from `proto-blue-api`).

## Requirements

- REQ-1: Lexicon JSON for at minimum four Polaris record types lives under
  `lexicons/` in the workspace root: `incident.json`, `observation.json`,
  `escalation.json`, `evidence-pointer.json`. Each is a valid Lexicon document
  per the proto-blue validator.
- REQ-2: A new `polaris-lexicons` workspace crate contains code generated by
  `proto-blue-codegen` from the JSON sources. The crate has no hand-written
  Rust in its `src/` tree (it is a pure codegen output crate, like
  `proto-blue-api`).
- REQ-3: A `proto-blue-codegen` build step regenerates `polaris-lexicons` from
  `lexicons/*.json`. Codegen runs as a `cargo xtask gen-lexicons` task — not
  in a `build.rs` — so CI catches diff between checked-in code and current
  Lexicon JSON.
- REQ-4: Hand-written mapping functions live in
  `polaris-types/src/lexicon_mapping.rs` and convert between
  `polaris_types::{Incident, Observation, ...}` and
  `polaris_lexicons::{Incident, Observation, ...}`. Mapping is fallible —
  conversion errors are typed (`MappingError::FieldOutOfRange`,
  `MappingError::UnsupportedVariant`, ...).
- REQ-5: Round-trip is lossless for the field subset that exists in both
  representations. Fields present in one shape but not the other are
  documented in a `mapping-matrix.md` and exercised by property tests.
- REQ-6: A backwards-compatibility policy for v1 → v2 wire changes is checked
  in at `lexicons/README.md` covering: how to add a field, how to deprecate a
  field, how to bump a Lexicon revision, how to coordinate the
  `polaris-lexicons` crate version bump with `polaris-types` releases.
- REQ-7: The `polaris-lexicons` crate has no dependency on `polaris-backend`
  or `polaris-frontend` and is compatible with `wasm32-unknown-unknown` (the
  frontend will need it for federation-aware UIs in #43).

## Acceptance Criteria

- [ ] AC-1: `lexicons/*.json` validates with `proto-blue-lexicon`'s schema
      validator in a CI check.
- [ ] AC-2: `cargo xtask gen-lexicons` regenerates `polaris-lexicons/src/`
      and CI fails if the diff is non-empty (forces the checked-in code to
      stay in sync with the JSON).
- [ ] AC-3: A round-trip property test
      (`polaris-types -> polaris-lexicons -> polaris-types`) succeeds for at
      least 1000 randomly-generated `Incident`/`Observation` values via
      `proptest` over the documented in-both-representations subset.
- [ ] AC-4: `polaris-lexicons` builds for `wasm32-unknown-unknown` in CI.
- [ ] AC-5: A sample valid-Lexicon JSON document for each Polaris record type
      deserializes into the corresponding `polaris_lexicons::*` type without
      error.
- [ ] AC-6: `lexicons/README.md` documents the backwards-compat policy and at
      least one worked example of a non-breaking field addition.

## Architecture sketch

The split is: `polaris-types` is what Polaris's case store, pattern engine,
moderator API, and audit log work with — plain Rust, no Lexicon machinery,
fast to evolve internally. `polaris-lexicons` is what flows across instance
boundaries — Lexicon-validated, codegen-bound, evolves under a strict
revision policy. `polaris-types::lexicon_mapping` is the bridge.

**Why not just promote `polaris-types` to the wire format?** Two reasons.
First, the internal type evolves with Polaris's needs (a new field added in
a release should not require a Lexicon revision and a federation handshake);
the wire type evolves with the federation contract. Second, `polaris-types`
holds internal-only fields that should never cross instance boundaries
(moderator IDs, internal audit chain hashes, etc.) — the mapping layer is
the privacy boundary and gives a single place to enforce "this field is
never federated."

**NSID namespace.** The plan comment suggests `gay.dollspace.polaris.*`.
That's a defensible choice (Polaris's first operator owns
`dollspace.gay`) but it permanently couples the wire format identity to one
operator. The right namespace is a Q1 below. The decision binds the project
for the lifetime of the federation graph — NSIDs are a stable identifier
that downstream consumers compile into their code.

**Codegen integration.** `proto-blue-codegen` already drives
`proto-blue-api`. We invoke it via `cargo xtask gen-lexicons` (a workspace
xtask binary), reading `lexicons/*.json` and writing to
`polaris-lexicons/src/`. The generated crate has the same shape as
`proto-blue-api::generated::*` so downstream code feels uniform.

**Mapping strategy.** Hand-written conversion functions, one per type, in
`polaris-types/src/lexicon_mapping.rs`. Not a derive macro — the mapping has
real decisions in it (default-fill missing fields, drop internal-only
fields, normalize representations) that a macro cannot make for us.

**File layout.**
- `lexicons/incident.json` etc. — the Lexicon JSON sources.
- `lexicons/README.md` — backwards-compat policy.
- `polaris-lexicons/Cargo.toml` — `serde`, `serde_json`, `chrono`,
  proto-blue-lexicon runtime if needed, no `tokio` or other heavy deps.
- `polaris-lexicons/src/lib.rs` — module re-exports for the generated tree.
- `polaris-lexicons/src/generated/` — codegen output.
- `polaris-types/src/lexicon_mapping.rs` — bridge functions.
- `polaris-types/src/lexicon_mapping/error.rs` — `MappingError` enum.
- `xtask/src/gen_lexicons.rs` — codegen driver.

**Migrations needed.** None — this is additive. No existing `polaris-types`
shape changes, no DB migration, no API break.

**Backwards-compat story.** `polaris-lexicons` ships under a separate
semver track from `polaris-types`. A `polaris-lexicons` major bump is a
federation-network event (peers must coordinate). A `polaris-types` major
bump is a Polaris-internal event (one operator upgrade). The mapping layer
absorbs the impedance for as long as the two are reconcilable; when they
diverge in a way the mapping cannot bridge, the Lexicon gets a revision.

**Dependencies on other M5 issues.** Blocking dependency for #43 federation
(federation needs a wire format). Soft dependency for any future
ATProto-native interop tooling. Independent of #44-#49.

## Open questions

<!-- OPEN: Q1 -->
### Q1: NSID namespace selection

The plan comment proposes `gay.dollspace.polaris.*`. Options:

- **A. `gay.dollspace.polaris.*`** — uses the first operator's controlled
  domain. ATProto NSID convention is the reverse-domain pattern, and the
  domain owner controls the namespace. Concrete and defensible.
- **B. `org.polaris.*` or `polaris.tools.*`** — neutral project namespace.
  Implies a `polaris.tools` or `polaris.org` domain registration and
  control by a project entity rather than one operator.
- **C. `com.atproto.polaris.*`** — colocated with the upstream ATProto
  namespace. Strongest signal of "this is a standard" but requires
  agreement from Bluesky / the ATProto stewards before reserving the
  namespace.

Trade-offs: Option A ships today, locks future federation participants to
recognizing a single operator's domain as the canonical authority. Option B
requires domain acquisition first, scales better as the project becomes
multi-operator. Option C requires upstream coordination and may not be
granted.

**To resolve**: human decision — likely defer until the project-vs-operator
governance question is settled. Provisional path: ship A on `main` with the
explicit understanding that the namespace is renameable (codegen makes
renames cheap) up until the first cross-instance federation handshake.
<!-- /OPEN -->

<!-- OPEN: Q2 -->
### Q2: Parallel-types vs. hand-written-mapping vs. tag-the-existing-table

The plan comment explicitly flags this as a design-doc question. Options:

- **A. Parallel types via codegen (proposed).** Two types per record
  (`polaris_types::Incident`, `polaris_lexicons::Incident`), explicit
  mapping. Most flexible; highest maintenance overhead.
- **B. Hand-written shared type.** One Rust struct that derives both `serde`
  for internal use and matches the Lexicon shape exactly. Drops a layer of
  code but couples internal evolution to wire-format evolution.
- **C. Tag the existing table.** Keep `polaris-types::Incident` as the only
  type; serialize it differently when emitting via Lexicon. Requires a
  separate `serde` adapter; doesn't get static guarantees that the on-wire
  shape matches a checked-in Lexicon.

The proposed answer is A. Justification above ("the internal type evolves
with Polaris's needs; the wire type evolves with the federation contract").

**To resolve**: confirm during design review. The cost of A is real
(mapping functions, mapping tests, two-version coordination); the cost of B
manifests later when federation locks the schema and internal evolution
gets blocked on every change.
<!-- /OPEN -->

<!-- OPEN: Q3 -->
### Q3: Which records actually need to be NSIDs in v1 of the federation surface?

The plan lists four: `incident`, `observation`, `escalation`,
`evidence-pointer`. Federation use cases (#43) really only need
`escalation` and the records it references. Options:

- **A. Define all four upfront.** Most complete; biggest surface to keep
  stable.
- **B. Define only `escalation` plus minimally-embedded
  observation/evidence-pointer.** Narrower wire surface; defers
  `incident`-record federation until a use case demands it.
- **C. Define `escalation` only, with `subject` references opaque.** Even
  narrower; observations and evidence pointers stay internal.

Trade-off: every NSID committed to is a stability commitment. Lexicons are
not lightly evolved.

**To resolve**: pair-design with #43. The right answer is "exactly the
records federation needs, no more." Recommend B as the v2 baseline with A
as a follow-up issue once a richer cross-instance UX is on the table.
<!-- /OPEN -->

<!-- OPEN: Q4 -->
### Q4: Subject identity across instances

A `polaris.escalation` from instance X to instance Y must reference a
subject. ATProto subjects (accounts, posts) have DIDs/AT-URIs which are
globally unique. But Polaris subjects can also be lists, feeds, or
labeler-internal aggregates. Options:

- **A. NSIDs only reference ATProto-shaped subjects** (DID or AT-URI).
  Internal-only subjects are not federable.
- **B. NSIDs reference Polaris-shaped `SubjectId`** with a side
  `subject-metadata` record. Federable but every federation peer must agree
  on subject identity, which is hard.
- **C. NSIDs reference both:** structured field with `kind` discriminant.
  Most flexible; punts the harder question of cross-instance subject
  identity to the consumer.

**To resolve**: tied to #43 conflict-resolution design. Provisional answer:
A. Federation that targets non-ATProto subjects is a much larger problem
and out of v2 scope.
<!-- /OPEN -->

## Out of scope (within this issue)

- The federation wire protocol itself (handshake, transport, signature
  validation across instances) — that lives in #43.
- Migrating the existing internal `polaris-types` to use the new
  `polaris-lexicons` types directly. The mapping layer is the contract; the
  internal types stay plain Rust.
- Federation conflict resolution semantics (what happens when two
  instances issue contradictory labels). #43 territory.
- Defining NSIDs for moderator-internal artifacts (audit log entries,
  exposure tracking, calibration data). These are by design not federable.
- Lexicon versioning runtime: there is no built-in Lexicon versioning in
  ATProto; we use codegen-time identity and a documented compat policy.
  This issue does not invent a runtime versioning system.

## Suggested decomposition

1. **PR 1 — Lexicon JSON drafts.** Author `lexicons/incident.json`,
   `observation.json`, `escalation.json`, `evidence-pointer.json` and the
   compat policy doc. No Rust changes. Reviewable as a wire-format spec by
   itself.
2. **PR 2 — `polaris-lexicons` crate + codegen task.** Add `xtask
   gen-lexicons`, generate the crate, wire CI to enforce "regenerate is a
   no-op." No mapping yet; the crate is consumable by external tooling
   already.
3. **PR 3 — Mapping layer + tests.** Add
   `polaris-types/src/lexicon_mapping.rs`, the `MappingError` enum, and
   round-trip property tests. This is the PR where the contract between
   internal and wire types actually lands.
4. **PR 4 — Wasm CI + documentation.** Verify `polaris-lexicons` builds for
   `wasm32-unknown-unknown`; write `lexicons/README.md`; document the
   field-by-field mapping matrix.

Each PR is small, reviewable, and lands a clean checkpoint. PRs 2-4 cannot
be done out of order. PR 1 can be reviewed and merged independently for
spec-only feedback before code lands.
