# Polaris upgrade guide

How to roll a running Polaris compose stack forward to a newer
`ghcr.io/dollspace-gay/polaris-backend` image without losing your
signing key, your moderation history, or your sanity.

This guide is for the compose / single-host posture documented in
[`quick-start.md`](quick-start.md). For Kubernetes upgrades see the
chart README at [`deploy/helm/README.md`](../../deploy/helm/README.md);
for the systemd posture see
[`deploy/systemd/README.md`](../../deploy/systemd/README.md).

## TL;DR

For a routine point upgrade on a healthy stack:

```sh
# (optional) pin a specific tag in deploy/.env first; see "Pinning"
docker compose -f deploy/docker-compose.yaml pull
docker compose -f deploy/docker-compose.yaml up -d
```

Polaris auto-runs `sqlx` migrations on boot. The signing key, the
Postgres data, and the evidence-CAR blobs all live on named volumes
and survive the image swap.

## Before you upgrade

Run through this checklist *before* you pull a new image.

- **You have a recent backup.** Check [`backup.md`](backup.md) for the
  PITR posture and the quarterly restore-drill SOP. A destructive
  migration that lands in a new image is unrecoverable without a
  backup — Polaris ships no automatic rollback for schema changes.
- **Your signing key lives on a volume**, not on the container's
  layer. The default `deploy/docker-compose.yaml` mounts the
  `polaris-keys` named volume at `/etc/polaris/keys:ro`; the
  K-256 keypair generated by the in-browser setup wizard lands there
  and persists across `docker compose pull` / `up -d` cycles. If you
  have bind-mounted the key from the host instead, the host file is
  the source of truth and equally survives the upgrade.
- **You know which tag you're going to.** For production, pin a
  specific release tag (see "Pinning" below) rather than chasing
  `:latest`. Pinning makes the upgrade reproducible and the rollback
  obvious.
- **You have read the release notes.** Check
  [`CHANGELOG.md`](../../CHANGELOG.md) for the diff between your
  current version and the target tag — especially any entries under
  **Changed** or **Removed**, which are the categories that trigger
  destructive migrations.

## Standard upgrade flow

The shipped path. Most upgrades are this and only this.

1. **Pin the new tag** in `deploy/.env` (skip if you intentionally
   track `:latest`):

   ```sh
   # deploy/.env
   POLARIS_IMAGE_TAG=vX.Y.Z
   ```

2. **Pull the image:**

   ```sh
   docker compose -f deploy/docker-compose.yaml pull polaris-backend
   ```

   The published image is multi-arch (linux/amd64 + linux/arm64) and
   the manifest resolution is automatic — you do not need to specify
   the platform.

3. **Restart the stack:**

   ```sh
   docker compose -f deploy/docker-compose.yaml up -d
   ```

   Compose recreates only the `polaris-backend` service (the
   Postgres, Redis, NATS, and Caddy containers keep running) and
   waits for the new container's `/healthz` probe to pass before
   considering the service healthy.

4. **Validate** — see "Validating the upgrade" below.

The whole loop typically takes under a minute on a warm host. The
`polaris-backend` image is the only thing that changes; the
pinned Postgres / Redis / NATS / Caddy versions in
`docker-compose.yaml` are upgraded independently when the compose
file itself is updated upstream.

## Migration handling

Polaris uses `sqlx-migrate` for forward-only schema migrations.

- **On boot**, the backend connects to Postgres, reads the
  `_sqlx_migrations` table, and applies every migration whose ID is
  greater than the highest already-applied ID. Bootstrap is automatic;
  there is no separate "run migrations" step.
- **The structured-log line** `Running database migrations` (followed
  by per-migration entries) tells you migrations are in progress.
  After they finish, the backend transitions to `Polaris backend
  starting version=…`. If you see a panic or a fatal log between
  those two events, the migration failed — the container will
  restart-loop, and rolling forward through the bad state requires
  hand intervention (see "Rolling back" below).
- **Verify the post-upgrade migration count:**

  ```sh
  docker compose -f deploy/docker-compose.yaml exec postgres \
    psql -U polaris -d polaris -c "SELECT COUNT(*) FROM _sqlx_migrations;"
  ```

  Compare with the file count under `polaris-backend/migrations/` for
  the tag you upgraded to.

- **Migrations are forward-only.** Polaris does not ship "down"
  migrations. A destructive change (e.g. dropping a column) cannot
  be reversed by replaying the previous image — the schema has
  already moved on. This is why the "you have a recent backup"
  checklist item is non-negotiable.

## Signing-key continuity

The labeler signing key persists across upgrades:

- In the **compose** deployment, the key file lives on the
  `polaris-keys` named volume mounted read-only at
  `/etc/polaris/keys` inside the container. `docker compose up -d`
  preserves named volumes; only `docker compose down --volumes`
  destroys them.
- In the **systemd** deployment, the key file lives on the host
  filesystem (typically `/etc/polaris/keys/labeler.key`) and is
  read by the binary at boot.

You only need the `labeler-key-rotate` CLI for the rare case where
the key itself must change (compromise, migration to a different
custody mode). Routine version upgrades do **not** require key
rotation. See `docs/ops/key-custody.md` for the rotation procedure.

## Pinning to a specific version

For production deployments, pin the image tag in `deploy/.env`:

```sh
# deploy/.env
POLARIS_IMAGE_TAG=vX.Y.Z
```

where `vX.Y.Z` is a published release tag from the
[`publish-image`](../../.github/workflows/publish-image.yml) workflow
(triggered by `v*` git tags pushed to the upstream repo). The
workspace version that produced your build is in
[`Cargo.toml`](../../Cargo.toml) under the workspace `version` key.

`POLARIS_IMAGE_TAG=latest` (or leaving the variable unset / commented
out — `latest` is the default in `docker-compose.yaml`) tracks the
tip of `main` and is fine for non-production installs. For anything
serving real moderators, pin.

You can also pin by short SHA — the publish workflow emits
`:main-<short-sha>` tags on every push to `main` — but the
human-readable release tag is preferred because it correlates with the
CHANGELOG.

## Rolling back

If the upgrade reveals a regression, roll back by re-pinning the
previous tag and restarting:

1. Set `POLARIS_IMAGE_TAG=<previous-tag>` in `deploy/.env`.
2. `docker compose -f deploy/docker-compose.yaml pull polaris-backend`
3. `docker compose -f deploy/docker-compose.yaml up -d`

This works **only if no destructive migration ran during the
upgrade.** If the new image dropped a column, renamed a table, or
removed a constraint, the previous image will fail at boot when its
queries hit the changed schema. In that case:

- Restore Postgres from the most recent PITR snapshot taken
  *before* the upgrade.
- Then re-pin the previous tag and `up -d` against the restored
  database.

The CHANGELOG entry for any destructive migration calls it out
explicitly. If you skipped reading the changelog before upgrading,
this is the line item that bites.

## Validating the upgrade

After `docker compose up -d` returns, walk this short checklist:

1. **`/healthz` returns 200:**

   ```sh
   curl -fsS https://<your-hostname>/healthz
   ```

2. **Structured-log version line matches the new tag:**

   ```sh
   docker compose -f deploy/docker-compose.yaml logs polaris-backend \
     | grep "Polaris backend starting"
   ```

   Expect a line like `Polaris backend starting version=vX.Y.Z` (or
   the workspace `version` for un-tagged builds; the current
   workspace is at `0.1.0` per [`Cargo.toml`](../../Cargo.toml)).

3. **Case view loads:** open
   `https://<your-hostname>/cases/<any-existing-case-id>` in the
   browser — confirm the action composer, third-party labels panel,
   and audit timeline all render.

4. **Subscribers reconnect:** the structured log should show
   `appview subscriber connected` (or equivalent reconnect lines)
   within ~10 seconds. The label firehose has a brief reconnect
   window during a restart; AppViews handle this automatically.

5. **Migration count is sane:** see the `_sqlx_migrations`
   `SELECT COUNT(*)` query in the "Migration handling" section.

If any of the above fails, capture
`docker compose -f deploy/docker-compose.yaml logs polaris-backend`
and open an issue at <https://github.com/dollspace-gay/polaris/issues>.
Roll back per the procedure above if the regression is service-
affecting.
